# fpdiff — formal divergence triage for floating-point RTL

`git diff` for FP hardware semantics, on a fully open toolchain. Point it at two
implementations of the same FP operation; it formally diffs them, decodes every
divergence into IEEE-754 terms, lets a human adjudicate each divergence class, and
turns accepted deviations into signed, machine-checked waivers. The output is a
**compatibility profile**: exactly where and how a design departs from its reference,
with a solver proof covering everything else.

Born from the observation that [Formal that "Floats" High](https://arxiv.org/abs/2512.06850)
(RTL-to-RTL model checking of FP arithmetic) runs on Cadence Jasper — while everything
it needs for the safety-equivalence core is expressible on Yosys + btor2 + btormc.

## Requirements (all open source)

- `yosys` ≥ 0.36 (brew or [oss-cad-suite](https://github.com/YosysHQ/oss-cad-suite-build))
- `btormc` and `iverilog` (both in oss-cad-suite)
- Python ≥ 3.10, stdlib only

If tools aren't on `PATH`, set `FPDIFF_TOOLS=<oss-cad-suite>/bin`.

## Quickstart

```bash
cd fpdiff
python3 -m fpdiff run examples/01_selfcheck.json     # hardfloat add vs itself: PROVED, ~0.03s
python3 -m fpdiff run examples/02_mutant.json        # vs rounding-bug mutant: 3 divergence classes
python3 -m fpdiff run examples/03_openfloat.json     # OpenFloat vs hardfloat: the real thing
python3 -m fpdiff triage examples/03_openfloat.json  # adjudicate; waivers re-run formal
python3 -m fpdiff report examples/03_openfloat.json  # emit the compatibility profile
python3 -m fpdiff coverage examples/03_openfloat.json # what your waivers left verified
```

## How it works

1. **Miter**: both designs are read into Yosys, flattened, renamed, and instantiated in
   a generated wrapper that feeds them identical inputs (with delay-register alignment
   for pipelined designs), applies waiver `assume`s, and `assert`s the (possibly
   waiver-relaxed) output comparison once pipelines fill.
2. **Check**: the miter goes to btor2 and btormc. Depth-0 BMC of a combinational miter
   is a *complete* equivalence proof; pipelined designs get bounded checking to `kmax`
   (reported honestly as bounded).
3. **Validate**: every counterexample is replayed through Icarus Verilog on each design
   independently. A finding is only reported when two unrelated tools agree.
4. **Explore**: the counterexample's input-class pair — (zero | subnormal | normal |
   inf | nan)² — is auto-blocked and the check re-run, enumerating at most one exemplar
   per divergent class pair (≤ 25 solver calls, typically well under a second each).
5. **Triage**: a human issues verdicts. *Bug* stays in the ledger as an open bug.
   *Accepted deviation* becomes a signed waiver — an input-class assumption or an output
   relaxation (NaN-payload canonicalization, N-ulp tolerance) — and the formal check
   re-runs under it. The solver adjudicates facts; the human adjudicates intent.
6. **Report**: a markdown profile: verdict, signed waiver table, exemplar findings, and
   what remains formally covered (`coverage` warns if a waiver assumed away a whole class).

The optional LLM assist (`fpdiff explain`) drafts a triage narration for a finding.
It is deliberately never an oracle: solvers and simulators produce the facts.

## Job files

```json
{
  "name": "openfloat_add32_vs_hardfloat",
  "format": {"exp": 8, "sig": 24},
  "gold": {"files": ["rtl/FPADD_8_24.sv"], "top": "FPADD_8_24",
           "ports": {"a": "io_in_a", "b": "io_in_b", "out": "io_out",
                     "clock": "clock", "reset": "reset"},
           "latency": 0},
  "gate": {"files": ["rtl/FP_add_32_1.sv"], "top": "FP_add_32_1",
           "ports": {"a": "io_in_a", "b": "io_in_b", "out": "io_out_s",
                     "clock": "clock", "reset": "reset",
                     "valid_in": "io_in_valid", "en": "io_in_en",
                     "valid_out": "io_out_valid"},
           "latency": 1},
  "waivers": "03_openfloat.waivers.json",
  "kmax": 6
}
```

`ports` maps the roles fpdiff understands onto your pin names; `tie` (port → constant)
handles anything else (rounding-mode pins, etc.). Example RTL under `examples/rtl/` is
generated by [openhwfp-eval](https://github.com/hwspec/openhwfp-eval)'s
`GenerateAllTestModules` (berkeley-hardfloat and OpenFloat wrappers).

## First real findings (2026-07-10, OpenFloat `FP_add_32_1` vs hardfloat RNE)

All 25 input-class pairs diverge on first contact. Each finding below was
solver-found and independently sim-confirmed; total solver time under 3 seconds.

- **`0 + 0 = 2.35e-38`** — OpenFloat saturates biased exponents to ≥ 1, so zero
  inputs become min-normals and their "sum" is `2^-125`.
- **`x + (−x) = 3.17e+29`** (at `x ≈ 8e36`) — exact cancellation does not produce
  zero, and the residual scales with the operand exponent. OpenFloat's own testbench
  comment ("1.0 + -1.0 ⇒ tiny residual", `absTol=1e-6`) treats a symptom of this at
  exponent 0; formally it is unbounded in absolute terms.
- **Unbounded ulp error under near-cancellation** — alignment truncation has no
  guard/sticky compensation, so cancelling operands amplify the rounding error:
  a ulp-tolerance sweep (1, 2, 4, 8, 16) never converges, with a 524288-ulp exemplar
  from operands one bit apart. Well-conditioned adds stay within ~1–2 ulp.
- **No gradual underflow** — results that are subnormal in IEEE are clamped to zero
  or min-normal (captured as the `output_subnormal_flush` waiver kind).
- **No NaN/inf semantics** — special exponents are saturated like any large value.

Contrast with openhwfp-eval's random simulation (24 vectors, `relTol=1e-5`), which
these implementations pass: random vectors essentially never cancel, so the dominant
error mechanism of this adder is invisible to that methodology.

## Known limitations (PoC)

- One exemplar per input-class pair; behaviors *within* a class pair beyond the first
  are only covered once waivers/blocks force the solver past them.
- Bounded (not inductive) checking for pipelined designs; `kmax` defaults to latency+3.
- Two-input, one-output ops only (add/sub/mul shapes). FMA/div/sqrt handshakes: next.
- The ulp-tolerance waiver treats inf as adjacent to max-normal (encoding order), so it
  also masks overflow-to-inf vs saturate-to-max differences — see waiver note.
- btormc only (rIC3/pono/avy consume the same `miter.btor`; drivers are ~10 lines each).
